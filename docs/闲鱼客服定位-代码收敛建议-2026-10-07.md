# 闲鱼卖家客服定位：代码收敛建议

后续状态：本建议中的消息接入、白名单、商品审核、知识范围与卖家工作台已于同日实现，见 [实施记录](闲鱼主线改造-2026-10-07.md)。下文保留改造前的检查结果与行号。

核对日期：2026-10-07。项目主定位调整为闲鱼个人卖家的智能客服 Agent，围绕买家、当前二手商品、卖家授权与人工核实展开。

本轮检查业务 Workflow、闲鱼侧车、知识检索契约及前端入口，并对侧车消息处理函数做离线输入复现。未连接闲鱼或服务器，未修改业务代码。

## 已有能力应继续保留

- `WorkflowEligibilityPolicy` 已把渠道资格检查从通用 Router 拆出；闲鱼默认排除订单、退货与保修流程。
- `ProductAdvisoryWorkflow` 与通用兜底已有当前商品事实、已售保护和闲鱼回复口径。
- `BargainWorkflow` 已按卖家授权确定性报价，保存跨轮报价，确认时复核库存、价格和授权。
- 卖家人工消息同步、暂停/恢复、待同步商品事实跨重启保留已实现。
- SLA v1 核实工单、结果回调去重、持久化快照、结果撤回与重启读取已实现并有联调记录。
- Runtime、Capability Gateway、认证、Outbox、执行预算、Trace 和评测仍是可复用的工程基础。

## 第一优先级：平台消息接入

### 同步包的批量处理与重复投递

`sidecar/xianyu/main.py:935` 只读取 `syncPushPackage.data[0]`，后续记录不进入处理。当前 `handle_message` 没有保存入站事件去重状态，`CsAgentClient.chat` 与 `ChatApiRequest` 也没有传递平台消息标识。

离线复现直接提取并执行现有 `handle_message` 函数，仅替换解密、网络和业务依赖，不修改函数主体：

| 输入 | 当前结果 |
| --- | --- |
| 同一同步包含两条合成买家消息 | 只处理第一条 |
| 完全相同的合成消息包投递两次 | 生成并发送两次回复 |

复现说明代码对这些输入的行为；没有声称本轮观察到了闲鱼线上重复投递。

建议逐条解析同步包，保留能够标识业务消息的稳定事件键，并传递到 Java 入口。去重状态需要区分已接收、正在处理、处理完成与发送结果未知，避免一次失败后永久丢弃消息。不能按正文去重，否则买家主动重复发送相同文本也会被吞掉；不能未经验证就把协议包 `mid` 当成所有子消息共用的业务主键。

### 接收循环与业务处理解耦

`sidecar/xianyu/main.py:1208` 的 WebSocket 接收循环直接等待 `handle_message`。该函数会等待 Java 回复、可选打字延迟和出站节流，一个买家处理期间后续买家消息、卖家接管指令和心跳响应都只能等待前一条处理结束。

建议接收循环只负责解析、协议应答和分发：普通买家消息在有界队列中按会话串行，不同会话可以有限并行；人工接管指令及时生效，发送前再检查暂停状态。避免直接为每条消息无界创建任务。

## 第二优先级：业务入口按闲鱼收敛

`XianyuScenarioProperties` 当前通过排除四个商城 Workflow 实现隔离。新增通用 Workflow 时默认仍可能进入闲鱼路由，`policy_qa` 目前就仍在候选范围内。

`PolicyQaWorkflow` 仍只认四份商城文档（退货、发票、配送、人工转接），并会追问发票、七天无理由等商城主题。闲鱼检索 Provider 已过滤商城知识，因此问题主要表现为进入一个没有可用闲鱼知识的流程，而不是演示政策直接泄漏。

建议闲鱼配置声明允许的 Workflow 与 Capability，采用正向准入；将订单、退货、保修和商城政策保留在独立演示配置中。新增或适配闲鱼交易咨询流程，覆盖卖家发货安排、包邮授权、配件/成色、商品核实和售后争议转卖家确认。平台规则只引用具有明确来源和版本的资料。

## 第三优先级：商品事实与知识分开建模

当前 `LocalKnowledgeSearchCapabilityProvider` 将闲鱼租户的 `product_category` 强制设为 `xianyu`。商品快照又以 `knowledgetype: POLICY` 入库。`TroubleshootingWorkflow` 请求的是 `TROUBLESHOOTING`，而当前仓库没有 `productcategory=xianyu` 的排查文档，所以默认闲鱼排查路径缺少匹配证据。

建议：

- 商品事实采用独立结构，保存价格、库存、标题、型号、成色、已知瑕疵、配件、来源、更新时间与版本；价格和库存继续沿用已有同步闸门。
- 闲鱼作为渠道/知识范围，耳机等作为品类，型号单独表示，避免一个字段承担两种含义。
- 说明书回答型号通常支持什么；卖家核实回答当前这一件是否正常；卖家规则回答可以承诺什么。
- 为主打商品补充可核查的说明资料与闲鱼 FAQ，再接入现有 RAG 通道；无证据时进入核实或人工流程。
- 商品描述和成色变化也需要审校、发布与版本管理。当前热更新主要覆盖价格与库存，描述仍依赖审校 Markdown 和重启加载。

## 后续产品收口

前端 `frontend/src/features/chat/data/scenarios.ts` 仍以退货、订单、偏好推荐作为默认入口；工作台使用演示身份与通用会话 ID，因此仅改提示词或按钮文本不会自动走到真实闲鱼流程。

建议主入口改为卖家工作台：商品事实与授权规则、买家会话、人工接管状态、核实工单及结果；原商城调试工具按演示入口保留。针对闲鱼主路径补齐批量消息、重复投递、会话顺序、人工接管打断、商品售出、授权撤销、事实同步失败和核实结果撤回的回归场景。

侧车目前会在 INFO 日志记录买家消息和机器人完整回复（`main.py:1027`、`main.py:1064`）；Java Trace 的脱敏不会覆盖这些日志。建议默认仅记录事件标识、消息类型、长度与处理结果，确需排障的文本走统一脱敏。

## 建议实施顺序

1. 修复批量消息处理、入站去重与接收循环阻塞。
2. 明确闲鱼允许的业务流程，并收口交易咨询与知识来源。
3. 将当前商品事实与型号知识分离，补齐商品审校更新和核实闭环。
4. 调整卖家工作台、主评测场景、README 与简历文案。

现阶段保持单体部署即可。多卖家账户体系、独立微服务和分布式消息系统应在明确需要之后再引入。
