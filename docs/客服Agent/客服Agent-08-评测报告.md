## 1. 评测范围

当前项目已经接入五类评测：

| 评测类型 | 用例文件 | Runner | 目标 |
| --- | --- | --- | --- |
| 路由评测 | `customer_service_eval_cases.json` | `CustomerServiceEvaluationTest` | 验证意图、Action、工具和转人工判断 |
| 知识库召回评测 | `knowledge_recall_eval_cases.json` | `KnowledgeRecallEvaluationTest` | 验证政策问题能否召回正确文档和关键政策点 |
| 回复质量规则评测 | `response_quality_eval_cases.json` | `ResponseQualityEvaluationTest` | 验证候选回复是否覆盖必要信息、是否出现危险承诺 |
| Agent 链路回复评测 | `agent_response_eval_cases.json` | `AgentResponseEvaluationTest` | 真实跑过 Agent / Runtime / Tool 后验证最终回复和 Trace |
| LLM-as-Judge 评测 | `llm_judge_eval_cases.json` | `LlmAsJudgeEvaluationTest` | 从准确性、完整性、客服语气、安全性四个维度评估回复 |

## 2.1 JSON 报告输出

当前评测 Runner 已经支持把指标落盘到 JSON 文件。

运行：

```powershell
mvn "-Dmaven.repo.local=.m2\repository" test
```

会在以下目录生成报告：

```text
target/eval-reports/
```

当前包含聚合入口、趋势入口、历史快照目录和四个明细文件：

| 文件 | 来源评测 | 内容 |
| --- | --- | --- |
| `summary.json` | 聚合报告 | 汇总当前已有评测报告和总体指标 |
| `trend.json` | 趋势报告 | 汇总最新指标、上一次指标和数值变化量 |
| `history/` | 历史快照 | 按评测类型保存每次运行的报告快照 |
| `customer-service-routing.json` | 路由评测 | 意图、Action、工具、转人工命中率 |
| `knowledge-recall.json` | 知识库召回评测 | 文档召回率、关键词覆盖率、topK 结果 |
| `response-quality.json` | 回复质量规则评测 | 判断一致率、正例通过率、负例拦截率 |
| `agent-response-chain.json` | Agent 链路回复评测 | 最终回复质量、Trace 事件覆盖率 |
| `llm-as-judge.json` | LLM-as-Judge 评测 | 四维度评分、Judge 判断一致率、问题原因 |

这些 JSON 文件属于构建产物，不需要提交到 Git。它们的价值是方便后续做趋势对比、自动生成评测报告，或者接入简单的 Monitor 面板。

## 3. 覆盖场景

路由评测覆盖：

- 订单查询：指定订单、缺少订单号追问、查询用户全部订单。
- 商品咨询：商品搜索。
- 退换货：退货进度、缺少退货单号追问、单轮退货申请、多轮退货申请。
- 知识库：退货政策、发票政策、保修政策、偏远地区配送。
- 人工转接：用户主动要求人工、投诉。
- 用户信息：查询用户基础信息。
- 闲聊：基础问候。

知识库召回评测覆盖：

- 超过 7 天是否还能退货。
- 商品质量问题售后检测。
- 电子发票开具时间。
- 企业发票信息要求。
- 保修期规则。
- 偏远地区配送规则。
- “耳机坏了能修吗”这类口语化保修问题。
- “一般几天能送到”这类口语化配送时效问题。

回复质量规则评测覆盖：

- 订单回复必须包含订单号、商品、状态和物流单号。
- 退货政策回复不能承诺无条件退款。
- 发票回复必须说明开具时间和企业发票所需信息。
- 转人工回复必须包含工单号。
- 错误样例需要被规则拦截。

Agent 链路回复评测覆盖：

- 订单查询：真实调用订单工具，再由 Fake LLM 生成稳定回复。
- 多轮退货申请：真实经过追问订单号、追问退货原因、提交退货工具、生成回复。
- 人工转接：真实创建模拟人工工单，并检查最终回复包含工单号。
- LLM 失败降级：模拟模型异常，验证工具成功后仍能返回模板化客服回复，并记录 `llm_failed`。
- Trace 检查：验证工具、LLM、转人工等关键事件确实出现。

LLM-as-Judge 评测覆盖：

- 安全的退货政策回复。
- 超过政策边界的无条件退款承诺。
- 订单查询回复信息不完整。

## 4. 当前价值

这套评测让项目不只是一个“能聊天的 Demo”，而是有可回归验证能力的 Agent 系统。

它可以证明三件事：

- Agent 决策链路是可测的：意图、Action、工具、转人工不是靠手动观察。
- 知识库检索是可测的：不只看是否调用了 `knowledge_search`，还看是否召回了正确政策点。
- 回复安全边界是可测的：危险承诺、漏关键字段可以被规则发现。
- Agent 链路回复是可测的：请求真实经过 Agent、Runtime 和 Tool，再检查最终回复与 Trace。
- 语义质量可以被第二层评估：LLM-as-Judge 会从准确性、完整性、语气和安全性给出结构化评分。

## 5. 面试表达

如果面试官问：“你怎么证明这个 Agent 有效果？”

可以这样回答：

> 我没有只做手动 Demo，而是做了离线评测集。路由评测会模拟多轮用户输入，验证意图、Action、工具和转人工判断；知识库召回评测会检查 topK 是否命中正确政策文档，以及检索文本是否覆盖关键政策点；回复质量规则评测会检查必要关键词和危险承诺；Agent 链路回复评测会真实跑过 Agent、Runtime 和 Tool，再检查最终回复和 Trace。当前路由 16 条、知识召回 8 条、静态回复质量 6 条、Agent 链路回复 3 条评测样本全部通过，并且每次运行都会生成 summary、history 和 trend 报告，方便观察质量变化。

如果面试官问：“LLM-as-Judge 是怎么做的？”

可以这样回答：

> 我没有用 LLM-as-Judge 替代规则评测，而是把它作为第二层语义评估。规则评测负责必要字段、危险承诺这类硬约束；Judge 评测负责准确性、完整性、客服语气和安全性四个维度。为了让普通 `mvn test` 稳定，我第一版使用 Fake Judge LLM 固定返回 JSON，先验证 Prompt、解析和报告链路，真实模型 Judge 后续作为可选评测开启。

如果面试官问：“现在评测还有什么不足？”

可以这样回答：

> 当前还不是完整线上级评测。路由和召回已经比较稳定，Agent 链路回复评测也已经跑过 Runtime 和 Tool，LLM-as-Judge 第一版也跑通了结构化评分链路，但 Agent 链路里的 LLM 和 Judge 仍然使用 Fake LLM，没有直接评估真实模型输出；评测用例数量也还偏少。后续我会把真实模型回复保存为 candidateReply，并扩充长尾口语、错别字、混合意图和情绪化表达。

## 6. 后续计划

下一步建议按这个顺序继续增强：

1. 把 Agent 链路回复评测从 Fake LLM 升级为可选真实模型输出。
2. 扩充评测集到 30 到 50 条。
3. 为知识库增加 query rewrite 和 rerank 前后的对比评测。
4. 把 LLM-as-Judge 从 Fake Judge 升级为可选真实模型 Judge。
5. 把 JSON 指标报告渲染成 Markdown 或 HTML，方便展示。
