# 客服Agent-25-面试亮点总结

## 1. 项目一句话

Smart CS Agent 是一个面向电商客服场景的任务型 Agent 系统，基于 Spring Boot + LangChain4j 构建。它不是只做聊天回复，而是把用户意图识别、多轮任务状态、业务工具调用、知识库检索、人工转接、Trace 可观测、Monitor 指标、用户反馈和离线评测串成一条完整链路。

面试时可以这样开场：

> 我做的是一个电商客服 Agent，不只是调用大模型生成回复，而是把客服任务拆成 Skill 决策、Runtime 执行、Tool 业务能力和 Monitor/Eval 质量闭环。系统能处理订单查询、退货申请、商品咨询、政策问答和人工转接，并且能通过 Trace 和评测集验证每一步是否可靠。

## 2. 面试主线

建议按这条顺序讲，逻辑会比较清楚：

1. 为什么选择客服 Agent。
2. 整体架构如何拆分。
3. 多轮会话如何保存状态。
4. 工具调用如何标准化。
5. RAG 如何避免模型乱答政策。
6. Trace 和 Monitor 如何定位问题。
7. Eval 如何让项目可验证。
8. 用户反馈如何沉淀成回归测试。
9. 当前不足和后续优化。

不要一上来堆名词。先讲“问题”，再讲“我怎么拆”，最后讲“如何证明它有效”。

## 3. 架构亮点

### 3.1 Skill / Runtime / Tool 分层

核心思想：

- `Skill` 负责判断当前应该做什么。
- `Runtime` 负责执行 `Skill` 规划出的动作。
- `Tool` 负责具体业务能力，比如查订单、查商品、退货、查知识库。
- `Trace` 负责记录执行过程。

可以这样讲：

> 我没有把所有逻辑都写在 Controller 或一个大 Service 里，而是把 Agent 拆成决策层、执行层和工具层。这样新增工具或调整某个意图时，不需要大改整体流程。

面试官可能追问：

**为什么不直接让 LLM 自己决定所有工具调用？**

回答思路：

> 客服场景里有很多高频且边界明确的任务，比如订单号、退货原因、人工转接，这些用规则更稳定、更可测。LLM 更适合处理语言表达和兜底回复。我的设计是规则优先，LLM 辅助，而不是把所有控制权都交给模型。

### 3.2 多轮会话与任务状态

项目把一次请求、跨轮状态和本轮执行上下文拆开：

- `ChatRequest`：当前这一轮用户输入。
- `ConversationState`：跨轮保存的会话状态和任务槽位。
- `TurnContext`：本轮执行过程中产生的观察结果、Trace 和最终回复。

可讲示例：

```text
用户：我要退货
Agent：请提供订单号
用户：ORD-004
Agent：请说明退货原因
用户：质量问题
Agent：已为你提交退货申请
```

这条链路体现了 Agent 不只是单轮问答，而是能记住“上一轮正在收集退货申请所需信息”。

### 3.3 MCP-style 工具层

工具层已经有统一结构：

- `ToolDefinition`
- `ToolCall`
- `ToolResult`
- `inputSchema`
- `outputSchema`
- `/api/mcp/tools`
- `/api/mcp/tools/call`

可以这样讲：

> 我先做了一个本地 MCP-style 工具边界，让每个工具都有名称、描述、输入 schema、输出 schema 和统一返回结构。这样做的好处是工具可以被 Agent 调用，也可以被前端和测试直接检查。后续如果要迁移到独立 MCP Server，边界已经比较清晰。

注意不要说“已经完整实现 MCP 协议”。更稳妥的说法是：

> 当前是 MCP-style Adapter，重点是工具协议边界和 schema 标准化，不是完整 MCP Server。

### 3.4 RAG 知识库检索

项目用 Markdown 知识库承载客服政策，并做了：

- 查询改写。
- 多路召回。
- 简单 rerank。
- `knowledge_miss` Trace。
- 知识库召回评测。

可讲取舍：

> 我没有一开始就引入向量数据库，因为项目当前知识量不大，而且我希望先把召回链路、Trace 和评测做清楚。Markdown 检索虽然简单，但可解释、可调试，适合项目早期验证 RAG 流程。

### 3.5 Trace 可观测

Trace 能看到：

- 会话开始。
- 命中的 Skill。
- 规划出的 Action。
- 工具调用参数。
- 工具结果。
- LLM 调用和失败。
- 最终回复。
- 耗时信息。

面试表达：

> Agent 最大的问题之一是黑盒。我给每轮对话都记录 Trace，前端也能查看。这样当用户说回答不对时，可以定位是意图错了、槽位没抽到、工具失败、知识库没召回，还是 LLM 回复质量不好。

### 3.6 Monitor 与用户反馈闭环

当前 Monitor 能聚合：

- 工具成功率。
- LLM 失败率。
- 转人工次数。
- 平均耗时。
- 用户反馈有用率。
- 负反馈问题类型。
- 结构化风险告警。

反馈闭环链路：

```text
用户点击无用
-> 后端记录 Feedback
-> 生成 Eval 候选样本
-> 人工审核 APPROVED / REJECTED
-> 导出 Eval case 草稿
-> 人工补齐断言
-> 合并进正式评测集
-> 后续回归测试覆盖
```

这部分是项目最值得讲的亮点之一，因为它说明你不仅会“做功能”，也在思考“如何持续改进 Agent 质量”。

### 3.7 离线评测体系

项目现在有五类评测：

- 意图和路由评测。
- 知识库召回评测。
- 回复质量规则评测。
- Agent 链路回复评测。
- LLM-as-Judge 评测。

面试表达：

> 我不只看 Demo 是否能跑，还给不同模块设计了评测集。规则评测保证稳定性，LLM-as-Judge 用来补充主观回复质量判断。默认测试用 Fake Judge，避免 CI 或本地测试依赖外部模型；需要时可以手动运行真实 Judge 脚本。

## 4. 简历推荐写法

### 4.1 简历一句话

智能客服 Agent：基于 Spring Boot + LangChain4j 实现电商客服 Agent，采用 Skill / Runtime / Tool 分层架构，支持多轮任务状态、MCP-style 工具调用、RAG 知识库、Agent Trace、Monitor 反馈闭环、LLM-as-Judge 与离线评测，提升客服场景下大模型应用的可控性、可观测性和可验证性。

### 4.2 简历项目描述

可以写成 3 到 5 条：

- 设计 Skill / Runtime / Tool 分层架构，将意图识别、工具调用、业务查询、知识库检索和回复生成解耦，支持订单查询、商品咨询、退货申请、政策问答和人工转接等客服场景。
- 实现多轮会话状态管理，使用 `ConversationState` 保存任务槽位、短期消息窗口和摘要记忆，支持退货申请等跨轮槽位填充流程。
- 设计 MCP-style 工具注册与调用层，统一 `ToolDefinition`、`ToolCall`、`ToolResult`、`inputSchema` 和 `outputSchema`，并提供 MCP Adapter 接口暴露工具列表和工具调用能力。
- 构建 Agent Trace、Monitor 指标和用户反馈闭环，将无用反馈沉淀为 Eval 候选样本，支持审核、导出、半自动合并正式评测集和回归测试。
- 建设五类离线评测，包括路由评测、知识库召回评测、回复质量规则评测、Agent 链路评测和 LLM-as-Judge 评测，并输出 JSON 报告、历史快照和趋势指标。

## 5. STAR 讲法

### S：背景

电商客服问题高频、重复，但又涉及订单、商品、售后政策和人工转接等多个业务系统。单纯把用户问题发给大模型容易出现乱答、漏问信息、工具调用不可控和质量难评估的问题。

### T：目标

构建一个可解释、可扩展、可评测的客服 Agent，让它能够完成真实客服任务，而不是只生成聊天文本。

### A：行动

我把系统拆成 Skill 决策层、Runtime 执行层和 Tool 工具层；为工具设计统一 schema 和返回结构；用 `ConversationState` 管理多轮任务状态；用 Markdown 知识库做 RAG 政策问答；用 Trace 记录每轮执行链路；最后补充 Monitor、用户反馈和离线 Eval，让系统质量可以持续验证。

### R：结果

项目支持订单查询、商品咨询、退货申请、政策问答、人工转接等核心客服场景；前端可以查看 Trace、Memory、Tools、Monitor 和 Eval 报告；测试覆盖路由、RAG、回复质量、Agent 链路和 LLM-as-Judge，最近一次完整测试通过 99 个测试用例。

## 6. 高频面试问答

### Q1：这个项目和普通 ChatBot 有什么区别？

普通 ChatBot 更关注生成回复，这个项目关注任务执行。它会识别意图、追问缺失信息、调用业务工具、检索知识库、记录 Trace，并通过 Eval 验证链路质量。

### Q2：为什么要拆 Skill、Runtime、Tool？

因为三者变化原因不同。`Skill` 变化来自业务策略，`Runtime` 变化来自执行机制，`Tool` 变化来自外部业务能力。拆开后更容易测试和扩展。

### Q3：为什么先做 MCP-style，而不是直接完整 MCP Server？

项目当前重点是把工具边界做清楚，包括工具定义、输入输出 schema、统一调用和错误处理。完整 MCP Server 会增加部署和协议复杂度，等本地边界稳定后再迁移更合理。

### Q4：RAG 为什么没有直接用向量数据库？

当前知识库规模较小，优先使用 Markdown + 查询改写 + 多路召回 + rerank。这样更可解释，也方便通过召回评测定位问题。后续知识量上来后，可以把 `KnowledgeTools` 的底层检索替换为向量检索。

### Q5：如何判断 Agent 回复质量？

项目用了多层评测。规则评测检查关键词、禁用词和结构化要求；Agent 链路评测检查完整执行结果；LLM-as-Judge 从事实一致性、帮助性、工具使用合理性和客服语气等维度评分。

### Q6：如果工具调用失败怎么办？

工具统一返回 `ToolResult`，失败时包含 `success=false`、`errorCode` 和错误信息。Runtime 会把失败记录到 Trace，LLM 失败时也有模板化降级回复，避免接口直接崩溃。

### Q7：用户反馈闭环有什么价值？

它把线上质量信号变成可回归测试资产。用户点“无用”后，系统生成候选样本，人工审核和补齐断言后可以合并进正式评测集。下次改代码或改 Prompt 时，这类问题就能被测试覆盖。

### Q8：项目目前最大的不足是什么？

可以坦诚说：

- 当前数据层是模拟仓储，还没有接真实数据库。
- 当前是 MCP-style Adapter，还不是独立 MCP Server。
- RAG 仍是轻量级本地检索，尚未接向量数据库和真实 rerank 模型。
- Multi-Agent 拆分还没有作为核心功能落地。
- Monitor 目前偏离线和本地演示，还没有接入真实生产监控系统。

然后补一句：

> 我没有刻意把所有高级概念一次性堆满，而是先把客服 Agent 的核心闭环做扎实，再逐步替换底层实现。

## 7. 面试演示建议

优先演示 3 条链路：

1. 多轮退货申请：体现任务状态和槽位填充。
2. 政策问答：体现 RAG、知识库召回和 Trace。
3. 质量闭环脚本：体现反馈如何进入 Eval。

不要现场演示太多功能。面试时间有限，演示越聚焦，项目越显得成熟。

## 9. 2 分钟版本

> 我做的是一个基于 Spring Boot + LangChain4j 的电商客服 Agent。它不是简单调用大模型聊天，而是一个任务执行系统。用户进来后，Agent 会先判断意图，如果信息不完整就追问，比如退货申请会先问订单号，再问退货原因；信息齐全后通过统一工具层调用订单、商品、退货、用户或知识库工具。
>
> 架构上我拆成 Skill、Runtime、Tool 三层。Skill 负责决策下一步动作，Runtime 负责执行动作，Tool 负责具体业务能力。工具层做了 MCP-style 标准化，每个工具都有 inputSchema、outputSchema 和统一 ToolResult，所以前端、测试和 Agent 都能用同一套边界。
>
> 为了避免 Agent 黑盒，我给每轮对话记录 Trace，能看到意图、Action、工具参数、工具结果、LLM 调用和耗时。为了验证质量，我做了五类离线评测，包括路由评测、知识库召回评测、回复质量规则评测、Agent 链路评测和 LLM-as-Judge。最后还做了 Monitor 和用户反馈闭环，用户点击无用后会生成 Eval 候选样本，审核和补齐断言后可以合并进正式评测集，形成回归测试。
