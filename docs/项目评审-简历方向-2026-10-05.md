这个项目可以作为简历主项目。它能展示任务编排、业务授权、副作用可靠性、检索和回归测试等多种工程能力。当前最值得投入的方向是修复实际边界问题、补充可复现的效果与性能证据，并把项目介绍收敛到少数能讲透的设计取舍。

**最值得在面试中展开的现有设计**

Runtime、Workflow、Action Handler、Capability Gateway 的职责划分有实际用途：任务状态、动作执行与能力实现可以独立变化。注册表、Skill 白名单以及保修扩展证明测试，比简单宣称“用了设计模式”更有说服力。入口与执行代码见 [CustomerServiceAgent](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/agent/CustomerServiceAgent.java:144)、[AgentRuntime](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/agent/AgentRuntime.java:159)。

副作用可靠性是最有价值的后端亮点之一。项目区分业务拒绝、技术失败和执行结果未知，采用稳定幂等键、租约、调用前准备 Outbox、人工处置与结果回放，能解释“请求超时后外部系统可能已经成功”这个真实问题。面试时重点讲执行顺序、故障窗口和恢复依据，避免把它概括成“加了重试”。入口见 [DefaultCapabilityGateway](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/capability/core/DefaultCapabilityGateway.java:164)。

可信 Principal、订单归属、业务唯一约束和工作流确认也各有作用。JWT 负责身份，归属校验负责对象访问，幂等负责同一操作去重，数据库约束处理不同请求竞争同一业务资源。把这些机制串成一条退货链路，能体现对并发和授权的理解。相关实现见 [ReturnApplicationService](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/domain/returnservice/ReturnApplicationService.java:57)。

RAG 按政策和故障知识采用不同策略，体现了业务取舍：政策强调准确条款，故障描述需要语义召回；向量失败后继续使用关键词结果。规则重排可以解释，但应准确称为规则重排，不应写成使用了训练过的语义重排模型。现有 Trace、Monitor、用户反馈审核与 Eval 回归，也形成了比较完整的质量改进路径。

真实模型对照报告有价值，尤其是它记录了基线胜出的场景、断言误报与 Judge 故障。这类实验复盘可以成为面试素材。不过，报告中的历史结论需要保留模型、样本与统计口径，不能直接当作当前代码的线上效果。

**优先修复的三个问题**

1. **[P1] 将评测基线入口从默认应用中隔离。**

   [BaselineChatController](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/eval/baseline/BaselineChatController.java:33) 无条件注册 `/api/chat/baseline/send`，而 [HttpSecurityConfiguration](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/security/HttpSecurityConfiguration.java:143) 允许 CUSTOMER 访问 `/api/chat/**`。基线故意移除了确认门控与 Skill 白名单，却调用同一套实际 Capability。因此普通认证用户可以走实验链路，绕过正式 Workflow 的确认步骤。现有 [BaselineAgentEvaluationTest](/Users/auska/csagent/src/test/java/com/smartcs/smart_cs_agent/eval/baseline/BaselineAgentEvaluationTest.java:127) 已明确断言“一轮内不经确认提交退货成功”，此次默认测试也通过了该用例。

   这个入口还使用只按 `conversationId` 索引的 [BaselineConversationStore](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/eval/baseline/BaselineConversationStore.java:26)。用户与租户不在 key 中，不同调用者提交相同 ID 时会共用历史，前一用户的对话或工具结果可能进入后一用户的模型上下文。

   建议将整套 baseline Bean 放到显式实验 Profile 或默认关闭的条件配置中，默认发布不注册该路由；实验中仍使用独立的内存业务数据。保留 CUSTOMER persona 做对照不妨碍在环境层隔离实验。基线历史也应使用完整 ConversationKey，身份隔离应作为两侧共有的基础条件。

   验收应包含：默认启动时路由不可用；显式实验配置下对照仍可运行；不同用户或租户使用相同 conversationId 时历史隔离。

2. **[P1] 给长期偏好记忆补上租户维度。**

   [UserMemoryStore](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/memory/UserMemoryStore.java:77) 的写入、读取和删除只接收 userId。[ChatApiController](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/controller/ChatApiController.java:262) 校验用户为本人后，也只把 Principal 的 userId 传入存储；UserProfileWorkflow 和商品推荐读取同样没有 tenantId。

   隔离复现中，租户 A 和 B 都有 `same-user`：A 写入偏好，B 通过现有 Controller 方法可以读到；B 清除后，A 的偏好也消失。会话、订单等组件已有租户隔离，偏好记忆仍是遗漏点。现有面试手册也承认这个边界，因此修复后再扩大相关简历表述。

   建议使用明确的 `UserMemoryKey(tenantId, userId)`，把写入、推荐读取、查询和清除四条调用链一起迁移。若进一步做 JDBC 持久化，也沿用该组合 key。验收要同时覆盖跨租户读、写、清除和推荐上下文。

3. **[P1] 在非开发配置中拒绝公开默认 JWT 密钥。**

   [SecurityProperties](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/security/SecurityProperties.java:116) 只在 `demoIssuerEnabled=true` 时拒绝已知开发密钥。默认关闭 Demo issuer 后，该密钥仍被 JWT Decoder 使用。隔离探针使用公开默认配置签发 ADMIN JWT，经过当前签名、issuer、audience、时间及 Principal 转换后获得管理员权限。

   Compose 的私有密钥必填约束已经降低了常规部署路径的风险，但直接运行 JAR、IDE 或另写部署脚本仍可能带默认值启动。关闭签发入口不会消除已知签名密钥的风险。

   建议把公开密钥限制在显式 local/test 配置；非开发环境缺少私有密钥、使用已知开发密钥或密钥长度不足时启动失败。验收同时覆盖 Demo issuer 开启和关闭两种情况。此发现不代表当前服务器已经使用了该默认密钥。

**修复后，最值得补的工程证据**

RAG 优先补真实检索对照和索引生命周期。目前知识库只有 10 份 Markdown，默认模式是 local，混合召回测试主要使用 Fake Embedding 与 Fake Vector Store。现有代码可以支持 Hybrid，但这些测试不能证明真实向量通道的召回收益。

此外，[QdrantVectorRetriever](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/knowledge/retrieval/QdrantVectorRetriever.java:49) 在在线查询时调用 `ensureIndex()`，首次请求会逐块生成整个故障知识库的向量并 upsert。代码能直接确认建索引位于查询链路；它造成多大延迟，本次未测量。建议将建索引移到显式导入或独立索引任务中，用内容哈希和版本决定是否重建，在线查询只生成查询向量。

为关键词、向量、Hybrid 建立同一份独立标注的留出集，包含口语改写、型号冲突、不存在条款与无答案问题。记录 Recall@K、排序质量、拒答正确率、端到端任务完成率、检索 P95 与模型调用成本。先用结果决定是否需要更复杂的重排模型；增加算法前应有可比较的基线。

后端优先补一个固定环境的并发与故障报告。测量无 LLM 的订单接口、有 LLM 的问答接口、同会话并发、跨会话并发，以及下游变慢和线程池饱和时的表现。报告机器配置、并发、吞吐、P50/P95/P99、队列拒绝、连接池等待与 JVM 内存，避免把个人项目的目标写成未经验证的高 QPS。

目前 [ConversationStore](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/agent/context/ConversationStore.java:197) 使用本地条纹锁串行执行整轮，跨实例依靠 Session CAS 检测冲突。这能检测保存冲突，但 CAS 失败不会撤回已经发生的外部操作。副作用还依靠稳定幂等键、领域唯一约束和 Outbox，是否能正确处理双实例竞争，需要单独验证。先明确单实例部署边界，再按实际需要做多实例实验。

Monitor 当前主要是进程内累计指标和少量近期记录。后续可接入标准指标与 Trace 导出，展示请求延迟分布、执行器利用率、队列拒绝与模型调用成本。用户偏好目前也是进程内存储，重启会丢失；如果继续称为长期记忆，应补持久化，或在介绍中明确它的生命周期。

**代码维护与测试改进**

[WorkflowRouter](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/workflow/core/WorkflowRouter.java:35) 已直接依赖闲鱼商品事实与场景配置，在首次评分和活跃任务恢复时执行渠道排除逻辑。排除发生在路由之前有业务理由，但通用 Router 依赖某个渠道，会让新增渠道继续修改核心。建议抽出 Workflow 可用性策略接口，让渠道组件提供策略，Router 只应用策略，并用包边界测试约束核心不依赖具体渠道。

ConversationState 约 900 行、MonitorService 约 870 行、BargainWorkflow 约 750 行。行数本身不是缺陷，但应检查是否已经承担多种独立变化。可以分别分离记忆管理、指标聚合与候选样本操作，以及报价计算与对话状态转换。清理过时 Phase 注释和重复教学注释，优先保留设计原因、约束和故障边界。

侧车 [test_echo_mode_never_writes_state_file](/Users/auska/csagent/sidecar/xianyu/tests/test_offline.py:510) 直接断言工作目录的 `data/sidecar-state.json` 不存在；已有 BRIDGE 状态文件时，即使 ECHO 没有写文件也会失败。此次在干净临时目录运行 26 项全部通过，说明需要修测试隔离，不能据此认定 ECHO 功能故障。测试应使用独立临时目录或验证目标文件未被修改，不能删除用户实际运行数据来让测试通过。

当前 CI 验证 Java 与前端，但未执行 Python 侧车测试。建议加上侧车离线测试；前端再补登录失效、切换身份时取消旧请求、退货多轮确认和人工处置四条关键浏览器流程。前端目前只接 Demo Token 获取接口，若计划作为实际产品提供页面，需要补真实身份系统接入。

MCP 建议补第三方客户端互通验收。[McpJsonRpcController](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/controller/McpJsonRpcController.java:38) 声明 `2024-11-05`，只处理 initialize、tools/list、tools/call，未处理该版本初始化后的 `notifications/initialized`。该通知属于声明版本的生命周期要求，依据见 [MCP 2024-11-05 官方生命周期规范](https://modelcontextprotocol.io/specification/2024-11-05/basic/lifecycle)。选择一个明确支持的协议版本，用标准客户端验证初始化、工具发现、调用、错误、鉴权与通知。自研 Client 和 Server 互相调用通过，仍不足以证明第三方兼容性。

**评测与简历表述需要收口的地方**

当前 [AgentRuntime](/Users/auska/csagent/src/main/java/com/smartcs/smart_cs_agent/agent/AgentRuntime.java:178) 明确注明专家域路由主要用于 Trace，执行选择仍由 WorkflowRouter 完成。现阶段使用“多 Workflow 任务编排”“专家域意图分类”更准确。没有独立专家 Agent 的执行、上下文交接和结果协调证据时，不应写成完成了多 Agent 协作。

默认 708 项测试中包含脚本模型；12 条知识召回样本全部命中，也不能换算成线上 RAG 准确率 100%。[77 号真实模型报告](/Users/auska/csagent/docs/客服Agent/客服Agent-77-真实模型对照实验报告.md:14) 的 v1 架构对照与 v2 修复前后实验使用不同模型通道，不能跨节拼数字。Judge 故障应作为评测不可用单独统计，原始与剔除故障后的口径都要保留。

此次工作区未找到报告引用的 v1 原始执行 JSONL 和聚合 JSON，因此可以审阅实验设计与历史报告，无法独立复算其真实模型数字。建议保存脱敏的逐次结果、场景和断言版本、模型标识、参数、Prompt 哈希与 Git 提交，避免原始证据只存在于会被清理的 target 目录。

报告中“模型凭空编造他人姓名和电话”的事件，宜归类为伪造个人信息或不安全生成；它与实际读取、泄露真实用户数据是不同失效模式。安全断言、业务完成、答案相关性和基础设施故障也应分开评分。非法用户请求被正确拒绝，不应仅因没有完成原请求而被算成业务能力失败。

**可采用的简历定位与文案**

项目名称建议用“面向电商客服的可控 Agent 系统”。项目介绍可写：

> 基于 Spring Boot 与 LangChain4j 实现任务型客服 Agent，覆盖订单查询、退货办理、政策问答、故障排查和人工转接；通过确定性 Workflow 管理关键业务流程，并结合证据约束的模型生成与工具能力网关完成客服任务。

根据岗位与篇幅，从下面四条中选择三到四条：

- 设计 Runtime、Workflow、Action Handler、Capability Gateway 分层，通过注册机制扩展业务流程，以统一 Capability 契约接入 Local/MCP Provider，支持多轮任务状态恢复与版本迁移。
- 针对退货和人工转接的重复请求、超时及结果未知，设计稳定幂等键、持久化租约、Outbox 和人工复核流程，并结合有界执行器与整轮预算控制资源占用。
- 按政策与故障知识构建差异化检索链路，支持字段加权关键词召回、可选 Qdrant 混合召回、RRF 融合和规则重排，提供向量通道降级与知识未命中处理。
- 建立 Trace、Monitor、反馈审核与 Eval 回归流程，维护 60 条六类对照场景；截至本次评审，默认后端测试 708 项中 707 通过、1 跳过，前端 10 项、侧车离线 26 项通过。

测试数只在确实有篇幅、能解释覆盖范围时使用。修复上述三个问题后，可再突出可信身份、租户边界与副作用确认；修复前应保留偏好记忆和实验入口的边界说明。真实模型收益只引用能够提供原始数据、明确口径的结果。

演示建议控制在五分钟：先跑一条完整退货确认链路，再展示一个外部超时后的结果未知与复核案例，最后展示一条真实 Hybrid 检索与无证据拒答。准备脱敏录屏作为环境故障时的备用材料。面试重点应落在“为什么这样设计、在哪个故障窗口起作用、如何验证”，并能解释取消等待与撤销操作的区别、会话 CAS 与业务幂等的区别，以及检索得分与回答正确性的区别。

建议实施顺序：先隔离实验入口、修偏好租户 key、收口 JWT 配置；随后补真实 RAG 对照与固定环境压测；最后整理 README、演示和简历，保留三到四条有证据的主线。
