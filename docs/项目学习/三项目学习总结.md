# 三个开源项目学习总结

## 项目来源

1. ecommerce-customer-service-skill-mcp - MCP 架构的电商客服
2. EchoMind - 智能客服 AI 系统（六大面试考点）
3. ecom-service-agent - 从0到1实战企业级电商客服 Agent

---

## 一、架构设计（来自项目 1）

### 核心思想：分层解耦

Agent Runtime    -> 会话管理、执行循环、LLM 调用
Skill            -> 客服策略、意图判断、回复组织
MCP Tools        -> 业务能力边界（订单、物流、售后等）
Knowledge Search -> 静态知识召回

### 各层职责

| 层次 | 负责 | 不负责 |
|------|------|--------|
| Agent Runtime | 会话状态、Skill 选择、Action 执行 | 具体客服业务规则 |
| Skill | 意图判断、客服流程、追问策略 | 直接访问数据库或外部系统 |
| MCP Tools | 订单、物流、支付、售后等业务能力 | 决定客服话术 |
| Knowledge | 商品、政策等静态知识召回 | 用户订单等私有数据查询 |

### 我们可以应用

- Tools 层只负责数据访问，不处理业务逻辑
- Skill 层负责对话策略，不直接访问数据
- Agent Runtime 负责编排，不沉淀具体规则

## 二、六大面试考点（来自项目 2）

### 考点 1：端到端意图识别

三路融合 + 加权投票：
- LLM 识别（语义理解强）
- 关键词匹配（速度快、成本低）
- 规则匹配（确定性高）

加权投票：综合三路结果，取置信度最高的

应用价值：比单用 LLM 更准确、更稳定

### 考点 2：MCP 工具调用框架

查询改写 + LLM 重排：
用户问题 -> 查询改写 -> 检索 -> LLM 重排 -> 返回结果

应用价值：解决召回不全、召回不好的问题

### 考点 3：多轮对话记忆管理

三级记忆 + 自动压缩：
- L1 工作记忆：最近 5 轮，完整保留
- L2 短期记忆：最近 20 轮，摘要压缩
- L3 长期记忆：历史所有，用户画像

应用价值：平衡上下文完整性和 token 成本

### 考点 4：多 Agent 路由编排

意图路由 + 性能路由 + 降级：
- 意图路由：根据意图分配到专门的 Agent
- 性能路由：负载均衡
- 降级：超时或失败时的兜底策略

应用价值：复杂场景下分工协作

### 考点 5：Monitor 闭环监控

在线表现驱动路由权重动态调整：
监控 -> 数据分析 -> 权重调整 -> 优化效果

应用价值：持续优化 Agent 质量

### 考点 6：端到端评测

LLM-as-Judge 四维度打分：
- 准确性：回答是否正确？
- 完整性：是否回答了所有问题？
- 相关性：是否紧扣问题？
- 流畅性：语言是否自然？

应用价值：量化 Agent 质量，驱动优化

## 四、Skill 策略包设计（来自项目 1 和 3）

### Skill 不是单个 Prompt

Skill 包含：
- manifest.yaml        # 元数据、能力声明
- SKILL.md             # 主策略说明
- references/
  - persona.md       # 角色与表达风格
  - intent.md        # 意图分类
  - policy.md        # 对话策略
  - templates.md     # 回复模板

### 我们可以应用

- 每个业务场景一个 Skill 定义
- Skill 与 Agent 核心分离
- 方便维护和扩展

## 五、Memory 记忆系统（来自项目 3）

### 三级记忆架构

Working Memory（工作记忆）：
  - 当前会话的完整消息
  - 保留最近 5 轮

Short-Term Memory（短期记忆）：
  - 会话内的关键事实
  - LLM 提取：订单号、用户偏好等

Long-Term Memory（长期记忆）：
  - 跨会话的用户画像
  - 持久化存储

### 我们可以应用

- 先实现滑动窗口（Phase 1 已完成）
- 后续加摘要压缩
- 最后加长期记忆

## 六、RAG 知识检索（来自项目 1 和 3）

### 两种方案

方案 A（项目 1）：结构化知识卡片
  - Markdown 文件按类别组织
  - L0/L1/L2 层级索引
  - 倒排索引 + 轻量 Rerank

方案 B（项目 3）：向量检索
  - 文档分块 -> Embedding -> 向量存储
  - 查询时向量相似度匹配
  - 支持 Chroma / Numpy 两种后端

### 我们可以应用

- 先用方案 B（向量检索），更通用
- 后续可以加 Query Rewriting 提升召回率

## 七、评测体系（来自项目 3）

### 双层评测

过程指标：
- 工具调用是否正确？
- 调用顺序是否合理？
- 是否有遗漏步骤？

结果指标：
- 回答是否准确？
- 是否完整？
- 是否流畅？

### LLM-as-Judge

让 LLM 当评委，从四个维度打分：
- 准确性（1-5 分）
- 完整性（1-5 分）
- 相关性（1-5 分）
- 流畅性（1-5 分）

## 九、面试时如何引用这些项目

### 说法参考

> 我参考了业界成熟的 Agent 架构设计，采用分层解耦的方式：
> Agent Runtime 负责执行循环，Tools 层定义业务能力，
> 两者通过接口解耦。这样设计的好处是，接入真实系统时
> 只需要替换 Tools 的实现，Agent 核心不用改动。

### 被问到"为什么这样设计"时

> 这种架构参考了 MCP（Model Context Protocol）的设计思想，
> 把业务能力边界和 Agent 执行逻辑分离。好处是：
> 1. 工具可复用，不同 Agent 可以共享同一套工具
> 2. 方便测试，可以用 Mock 数据开发，后续切换真实数据
> 3. 易于扩展，新增业务场景只需加新的 Tool
