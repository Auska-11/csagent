**Smart CS Agent｜闲鱼卖家智能客服系统**

**技术栈：** Java 17、Spring Boot、Spring Security、MyBatis、MySQL、LangChain4j、Python、SQLite、Docker。

**项目描述：** 面向闲鱼个人卖家的商品接待场景，开发支持商品咨询、授权议价、商品审核和人工接管的智能客服系统，使用 Python 侧车桥接平台消息与 Java 后端。

- **业务编排：** 基于 Runtime、Workflow、Action Handler 与 Capability Gateway 分层实现多轮业务流程；通过会话状态保存报价，确认时复核价格、库存和卖家授权，超出授权时转卖家处理。
- **消息可靠性：** 使用 SQLite 持久化收件箱、固定并发任务和同会话顺序处理接收平台消息；Java 侧结合事件标识、数据库唯一约束与结果回放处理重复请求，对执行或发送结果未知的消息停止自动重试。
- **权限与人工协作：** 基于 Spring Security/JWT、租户与能力白名单限制访问，按租户、用户和会话隔离状态；支持商品草稿审核发布、版本冲突校验和人工接管，并以 Trace 与故障回归验证关键流程。

如果 RAG 已经掌握，可作为第四条或替换第三条的一部分：

- **知识检索：** 将当前商品事实与型号知识分离，按渠道、品类和型号筛选资料；实现关键词与可选 Qdrant 混合召回、RRF 融合、规则重排及向量通道降级，证据不足时澄清或转卖家核实。

暂不写线上用户量、商业收益、性能提升百分比或模型准确率。当前没有依据把项目表述为官方闲鱼接口、完整分布式多 Agent 系统、自动下单退款系统或大规模生产服务。

## 4. 六道核心技术题

### Q1：为什么关键业务流程由 Workflow 控制？这算什么类型的 Agent？

● **核心关键词**：控制权、状态机、业务授权、确定性、模型职责。

● **回答范式**：

a. **核心结论**：当前是工作流驱动的任务型客服系统。流程选择和业务动作主要由代码控制，大模型参与部分回答，价格与授权承诺使用确定性逻辑。

b. **原理解读**：

- **约束关键结果**：模型文本不能替代卖家授权或库存事实。议价逻辑计算价格，直接构建买家回复。
- **保持多轮状态**：Workflow 保存报价和当前步骤；用户下一轮只说“好”也能恢复任务。
- **保留切换出口**：活跃任务通过 `acceptsMessage` 判断是否继续承接新消息，避免旧任务吞掉新问题。
- **拆分变化**：Runtime 管循环与预算，Workflow 管决策，Handler 管动作执行，Capability 管业务能力契约。

c. **场景举例**：报价后商品售出，确认请求重新检查库存，返回售出结果。

● **高频追问**：加入 LLM 是否就等于自主规划 Agent？

○ **回答**：关键在于谁决定下一步。当前控制流主要由代码定义，不能表述为模型自由规划多个 Agent。概念区分参考 [Anthropic 的 Workflow 与 Agent 说明](https://www.anthropic.com/engineering/building-effective-agents)。

### Q2：消息回执、会话 CAS、业务幂等各解决什么？

● **核心关键词**：事件标识、结果回放、并发覆盖、版本、副作用。

● **回答范式**：

a. **核心结论**：三个机制保护不同对象。消息回执防同一入站事件重复执行，会话 CAS 防旧状态覆盖新状态，能力幂等约束同一业务操作的重复副作用。

b. **原理解读**：

- **消息回执**：按身份作用域和 messageId 生成键，保存正文指纹；完成后回放结果，同 ID 内容冲突时拒绝。
- **会话 CAS**：保存状态时带读取版本，更新行数为零意味着版本冲突，不能覆盖。
- **能力幂等**：按稳定业务操作键保存执行状态与结果；不能因为重新进入同一流程就生成新键。
- **业务唯一约束**：不同操作键也可能竞争同一资源，例如同一订单的退货申请，因此还需要业务层约束。

c. **对比结论**：会话保存成功不能证明外部工单只创建一次，消息去重也不能覆盖所有业务入口。

● **高频追问**：为什么不按消息正文去重？

○ **回答**：买家可能主动连续发出同一句话，它们是不同业务事件。应该保留稳定事件 ID，再用正文指纹检查 ID 冲突。

### Q3：为什么超时后不能直接重试？Outbox 怎么用？

● **核心关键词**：结果未知、副作用、调用前记录、稳定幂等键、人工复核。

● **回答范式**：

a. **核心结论**：超时只说明没有在期限内拿到结果，外部系统可能已经执行。恢复是否安全取决于远端幂等或结果查询能力。

b. **原理解读**：

- **先留记录**：外部工单请求前写 PREPARED 记录，保存请求与稳定幂等键，留下恢复依据。
- **成功留结果**：拿到可信结果后确认记录，后续请求回放已确认结果。
- **未知单独处理**：调用中断或保存结果失败可能留下 PREPARED/RESULT_UNKNOWN，不能直接归类成业务失败。
- **有限恢复**：满足条件时使用原幂等键恢复；需要查询或人工判断时进入复核。Outbox 自身不保证远端不会重复执行。

c. **场景举例**：工单平台已经创建工单，返回响应时网络断开；用新键重试可能创建第二个工单。

● **高频追问**：线程超时后 `cancel(true)` 能撤销业务吗？

○ **回答**：它只是请求线程中断，底层库可能不响应，远端副作用也不会因此回滚。需要独立的业务状态和恢复机制。

### Q4：线程池、会话锁和整轮预算怎样配合？

● **核心关键词**：有界队列、拒绝策略、条纹锁、deadline、剩余预算。

● **回答范式**：

a. **核心结论**：用有限资源控制下游阻塞，同会话串行保护状态，并让排队和执行共享一份时间预算。

b. **原理解读**：

- **资源有界**：LLM 执行器使用固定上限的线程、`ArrayBlockingQueue` 与 `AbortPolicy`，饱和时返回结构化失败。
- **同会话串行**：ConversationStore 使用条纹 `ReentrantLock`，等待锁使用剩余期限，避免无限排队。
- **预算贯穿**：Agent 进入会话锁前建立 deadline；模型调用取单次调用限额与剩余预算的较小值。
- **独立通道**：侧车固定任务消费收件箱，卖家控制事件有独立处理路径；发送前重新检查接管状态。

c. **代码细节**：当前配置中 LLM 默认最多 8 个工作线程、队列容量 32、调用上限 12 秒；整轮默认 30 秒。这些是限制配置，尚无压测证明它们是最优参数。

● **高频追问**：为什么有了会话 CAS 还需要锁？

○ **回答**：CAS 在保存时发现覆盖冲突，本地锁减少同会话流程交错。副作用可能发生在保存之前，两者都不能替代能力幂等；本地锁也不能协调多个实例。

### Q5：如何防止越权和跨租户读取？

● **核心关键词**：可信 Principal、角色、资源归属、复合键、能力白名单。

● **回答范式**：

a. **核心结论**：身份来自经过验证的 JWT Principal，再分别校验接口权限、资源归属和能力准入。请求体和模型参数不能决定可信身份。

b. **原理解读**：

- **验证凭据**：Spring Security 校验签名、issuer、audience 和时间等，随后构建 Principal。
- **限制入口**：角色限制管理接口；卖家工作台还检查配置租户，其他租户 ADMIN 不等于本卖家管理员。
- **贯穿身份**：会话使用 tenantId、userId、conversationId 复合键；用户偏好也包含租户。
- **限制执行**：Workflow 资格与 Capability 白名单是不同执行边界，新增通用功能不能默认进入闲鱼。

c. **场景举例**：两个租户使用相同 userId 和 conversationId，状态仍应独立保存和读取。

● **高频追问**：只用 JWT 是否足够？

○ **回答**：JWT 证明请求身份，不自动证明对某个商品或业务资源具有操作权，还需要对象归属和业务授权校验。

### Q6：为什么商品事实和 RAG 知识分开？

● **核心关键词**：精确事实、知识范围、型号、混合召回、证据不足。

● **回答范式**：

a. **核心结论**：当前价格、库存和卖家核实结果需要精确读取；型号知识只能说明一般能力，不能证明当前这件二手商品状态正常。

b. **原理解读**：

- **事实独立**：平台价格库存覆盖与卖家发布资料一起提供事实；草稿不自动进入买家回复。
- **范围过滤**：知识按渠道、品类和型号约束，型号未确认时不能引用任意型号手册。
- **按任务检索**：政策使用关键词路径；故障在 Hybrid 模式增加向量路径，经 RRF 融合和规则重排选择候选。
- **降级有边界**：向量失败保留关键词通道；有召回结果仍需相关性判断，证据不足时澄清或核实。

c. **说明**：RRF 使用排名融合，代码中的重排是规则打分。混合检索机制可参考 [Qdrant 官方文档](https://qdrant.tech/documentation/search/hybrid-queries/)，项目实现位于 Java 策略类。

● **高频追问**：为什么不直接把底价塞进 Prompt？

○ **回答**：底价是内部授权信息，既不应泄露给买家，也不能让模型决定是否突破；当前代码由卖家规则服务读取并确定性计算。

先从现有需求中选择一个小改动，例如补充一个确实无法识别的买家出价表达。自己准备输入与预期结果、定位代码并说明修改范围，再使用 AI 辅助实现，最后读懂 diff 并验证已有授权与已售保护。

记录：问题是什么、为什么改这里、影响哪条链路、如何验证、是否引入误识别。如果现有代码已经正确处理该表达，就保留复现记录，换一个实际存在的问题。

### 练习三：亲自复现三类故障

- 报价后库存变为 0，随后买家确认，观察是否停止推进。
- 同 messageId 重复请求，观察业务调用次数与返回结果；再换正文触发冲突。
- 工单或发送结果未知，观察为什么不能自动按新请求重试。

保存脱敏输入、Trace、状态和结果。后续讲“我定位过一个问题”时，只选真实亲自完成的复现和修改。

### 如何回答“是不是 AI 写的”

目前可以直接说：“代码主要使用 AI 辅助生成，我正在通过走读、故障复现和修改掌握关键模块。”准备完成后，补充你亲自做过的具体工作，例如某个状态机修改或一次结果未知复现。

如果某个设计最初由 AI 提出，可以说明来源，再解释你如何理解它、验证它以及会在什么条件下换方案。个人职责以真实经历为依据。

### 与项目一起复习的 Java 后端知识

- 会话锁：`ReentrantLock`、`tryLock`、中断、锁粒度、条纹碰撞。
- 模型调用：`ThreadPoolExecutor` 参数、队列、拒绝策略、Future 超时和取消边界。
- JDBC 保存：主键与唯一索引、条件 UPDATE、受影响行数、事务边界。
- 权限：Spring Security 请求链、JWT 验证、身份与资源授权的区别。
- 状态持久化：JSON 编解码、schemaVersion、状态迁移和重启恢复。
- 外部接口：连接/读取超时、幂等键、退避重试、结果未知与补偿依据。

项目准备和 Java、MySQL、网络等基础学习一起进行。不要把项目中的类名当成原理解释。

## 7. 下一阶段补证据的顺序

1. **本地可复现演示**：正常议价、报价后售出、人工接管、重复消息四个场景。没有平台连接时，明确展示本地模拟输入。
2. **个人修改与排障记录**：至少一处能解释的变更和三类故障复现，形成真实可讲的经历。
3. **当前版本部署复验**：需要时重做 MySQL 与渠道验收，保留版本、环境和日志；历史成功记录不能代替当前版本验收。
4. **性能与 RAG 量化**：核心链路掌握后再做。压测分别统计确定性业务路径与模型路径；RAG 在固定标注集比较召回、拒答、耗时和调用成本。

保持现有单体部署，先完成以上证据。多实例需求明确后，再讨论共享商品资料存储、会话协调和未知回执复核等改造。

### 性能实验应记录什么

固定机器、数据库模式、数据集、并发量、测试时长和代码版本。确定性路径记录吞吐、P95、错误率和资源占用；模型路径另外记录模型、供应商、调用次数及超时。使用脚本模型得到的性能只描述本地工程路径，不表述为真实模型或平台吞吐。
