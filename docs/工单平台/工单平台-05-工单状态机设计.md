# 售后工单与 SLA 履约平台：工单状态机设计

## 1. 为什么需要状态机

工单系统的核心不是简单修改 `status` 字段，而是保证每一次状态变化都符合业务规则。

如果没有状态机，容易出现：

- 已关闭工单又被处理。
- 未分配工单直接解决。
- 已取消工单继续触发 SLA。
- 并发请求互相覆盖状态。
- 操作日志和真实状态不一致。

因此，工单状态只能通过明确动作触发，并由状态机校验。

## 2. 状态定义

| 状态 | 说明 |
| --- | --- |
| `CREATED` | 已创建，等待分配 |
| `ASSIGNED` | 已分配负责人，等待接单 |
| `PROCESSING` | 处理中 |
| `WAITING_CUSTOMER` | 等待用户补充信息 |
| `WAITING_SUPPORT` | 等待技术支持处理 |
| `RESOLVED` | 已解决，等待用户确认 |
| `CLOSED` | 已关闭 |
| `CANCELLED` | 已取消 |

## 3. 动作定义

| 动作 | 说明 |
| --- | --- |
| `ASSIGN` | 分配工单 |
| `ACCEPT` | 负责人接单 |
| `REQUEST_CUSTOMER_INFO` | 请求用户补充信息 |
| `CUSTOMER_REPLY` | 用户补充信息 |
| `TRANSFER_TO_SUPPORT` | 转技术支持 |
| `SUPPORT_FINISH` | 技术支持处理完成 |
| `RESOLVE` | 标记已解决 |
| `CLOSE` | 用户确认关闭 |
| `CANCEL` | 取消工单 |
| `REOPEN` | 重新打开 |

## 4. 状态流转表

| 当前状态 | 动作 | 目标状态 | 说明 |
| --- | --- | --- | --- |
| `CREATED` | `ASSIGN` | `ASSIGNED` | 系统或管理员派单 |
| `ASSIGNED` | `ACCEPT` | `PROCESSING` | 负责人接单 |
| `PROCESSING` | `REQUEST_CUSTOMER_INFO` | `WAITING_CUSTOMER` | 等待用户补充 |
| `WAITING_CUSTOMER` | `CUSTOMER_REPLY` | `PROCESSING` | 用户补充后继续处理 |
| `PROCESSING` | `TRANSFER_TO_SUPPORT` | `WAITING_SUPPORT` | 转技术支持 |
| `WAITING_SUPPORT` | `SUPPORT_FINISH` | `PROCESSING` | 技术支持完成处理 |
| `PROCESSING` | `RESOLVE` | `RESOLVED` | 标记解决 |
| `RESOLVED` | `CLOSE` | `CLOSED` | 用户确认或系统自动关闭 |
| `RESOLVED` | `REOPEN` | `PROCESSING` | 用户认为未解决 |
| `CREATED` | `CANCEL` | `CANCELLED` | 创建后取消 |
| `ASSIGNED` | `CANCEL` | `CANCELLED` | 分配后取消 |
| `PROCESSING` | `CANCEL` | `CANCELLED` | 处理中取消 |

## 5. 终态

终态包括：

- `CLOSED`
- `CANCELLED`

终态工单不能继续处理，只能查看。

## 6. 状态机伪代码

```java
public class TicketStateMachine {

    private final Map<TicketStatus, Map<TicketAction, TicketStatus>> transitions;

    public TicketStatus transit(TicketStatus current, TicketAction action) {
        Map<TicketAction, TicketStatus> actionMap = transitions.get(current);
        if (actionMap == null || !actionMap.containsKey(action)) {
            throw new IllegalStateException("Illegal ticket status transition");
        }
        return actionMap.get(action);
    }

    public boolean canTransit(TicketStatus current, TicketAction action) {
        return transitions.containsKey(current)
            && transitions.get(current).containsKey(action);
    }
}
```

## 7. 典型状态变更用例

分配工单：

- 当前状态是 `CREATED`。
- 操作人是管理员或系统派单任务。
- 目标负责人属于匹配技能组。
- 成功后状态变为 `ASSIGNED`，记录操作日志，发布 `TicketAssignedEvent`。

接单：

- 当前状态是 `ASSIGNED`。
- 操作人是当前负责人。
- 成功后状态变为 `PROCESSING`。
- 如果是首次响应，写入 `first_responded_at`，取消首响 SLA。

标记解决：

- 当前状态是 `PROCESSING`。
- 操作人是负责人、技术支持或管理员。
- 必须填写解决说明。
- 成功后状态变为 `RESOLVED`，通知用户确认。

重新打开：

- 当前状态是 `RESOLVED`。
- 用户认为问题未解决。
- 需要填写原因。
- 成功后状态变为 `PROCESSING`，重新生成解决 SLA 任务。

## 8. 并发控制

状态变更要避免两个请求同时修改同一工单。

推荐方案：

- 数据库乐观锁字段 `version`。
- 更新时带上当前版本。
- 更新失败则重新读取工单并提示重试。

```sql
UPDATE ticket
SET status = ?, version = version + 1, updated_at = ?
WHERE id = ? AND version = ?;
```

## 9. 面试表达

> 工单状态不是由接口直接传入并更新，而是通过动作驱动状态机流转。每个动作都会校验当前状态、操作人权限和业务前置条件。状态变更、操作日志和 Outbox 事件在同一个事务内完成，从而保证状态可追踪，事件可补偿。
