# 售后工单与 SLA 履约平台：MQ 与一致性设计

## 1. 为什么需要 MQ

工单系统中有很多动作不应该阻塞主流程。

适合异步化的场景：

- 工单创建后发送通知。
- 工单状态变更后同步 Elasticsearch。
- 工单关闭后刷新统计。
- SLA 超时后发送升级提醒。
- Agent 创建工单后回写处理结果。

如果这些动作都放在接口同步链路里，会导致接口变慢，且外部系统失败会影响核心业务。

## 2. 核心原则

- 核心业务数据以 MySQL 为准。
- MQ 用于异步通知和最终一致。
- 业务事务内不直接依赖 MQ 发送成功。
- 消费端必须支持幂等。
- 失败可以重试，重试仍失败进入死信或人工补偿。

## 3. 一致性问题

常见错误写法：

```text
保存工单到 MySQL
发送 MQ
返回成功
```

风险：

- MySQL 成功，MQ 失败：通知、搜索、统计都收不到事件。
- MQ 成功，MySQL 回滚：消费者读到不存在或不一致的数据。

## 4. Outbox 模式

本项目使用 Outbox 模式解决本地事务和消息发送的一致性问题。

```text
业务接口
  -> 开启本地事务
  -> 写 ticket
  -> 写 operation_log
  -> 写 outbox_event
  -> 提交事务

Outbox 发布任务
  -> 扫描 NEW 事件
  -> 发送 MQ
  -> 标记 PUBLISHED
```

这样可以保证：

- 只要工单创建成功，对应事件一定在数据库中。
- 即使 MQ 暂时不可用，也可以后续重试发布。

## 5. Outbox 事件状态

| 状态 | 说明 |
| --- | --- |
| `NEW` | 新事件，等待发送 |
| `PUBLISHING` | 正在发送 |
| `PUBLISHED` | 已发送 |
| `FAILED` | 多次发送失败 |

## 6. 发布任务设计

扫描 SQL：

```sql
SELECT *
FROM outbox_event
WHERE status IN ('NEW', 'FAILED')
  AND (next_retry_at IS NULL OR next_retry_at <= NOW())
ORDER BY created_at
LIMIT 100;
```

发布流程：

```text
查询待发布事件
  -> 尝试抢占事件
  -> 发送 MQ
  -> 成功则标记 PUBLISHED
  -> 失败则增加 retry_count 并计算 next_retry_at
```

抢占事件：

```sql
UPDATE outbox_event
SET status = 'PUBLISHING', updated_at = NOW()
WHERE id = ? AND status IN ('NEW', 'FAILED');
```

如果影响行数为 0，说明事件被其他任务抢占。

## 7. 消费幂等

MQ 可能重复投递，消费者必须幂等。

幂等方案：

- 每个事件有唯一 `event_id`。
- 消费前检查是否处理过。
- 消费成功后记录处理结果。
- 对于 ES 同步，可以按工单 ID 覆盖更新。
- 对于通知发送，可以使用唯一业务键防重。

可增加表：

```sql
CREATE TABLE consumed_event (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  event_id VARCHAR(64) NOT NULL,
  consumer_name VARCHAR(64) NOT NULL,
  consumed_at DATETIME NOT NULL,
  UNIQUE KEY uk_event_consumer (event_id, consumer_name)
);
```

消费流程：

```text
收到消息
  -> 尝试插入 consumed_event
  -> 插入失败说明已消费，直接返回成功
  -> 执行业务逻辑
  -> 提交事务
```

## 8. 重试与死信

生产端重试：

- Outbox 发布失败时 `retry_count + 1`。
- 设置 `next_retry_at` 延后重试。
- 超过最大次数后标记 `FAILED`。

消费端重试：

- 短暂异常可以重试。
- 参数错误或数据不存在不应无限重试。
- 多次失败进入死信队列或失败表。

死信处理需要记录：

- 原始事件。
- 失败原因。
- 失败次数。
- 最后失败时间。

## 10. 典型消费者

| 消费者 | 订阅事件 | 作用 |
| --- | --- | --- |
| `NotificationConsumer` | 创建、分配、状态变更、SLA 超时 | 生成站内信 |
| `SearchIndexConsumer` | 创建、状态变更、回复 | 同步 ES |
| `StatisticsConsumer` | 创建、关闭、超时 | 更新统计指标 |
| `SlaConsumer` | 状态变更 | 取消或更新 SLA 任务 |

## 11. 面试表达

> 我没有在业务事务里直接发送 MQ，而是使用 Outbox 表。工单主数据、操作日志和事件记录在同一个本地事务中提交，后台发布任务再把事件发送到 MQ。消费者侧通过 `event_id + consumer_name` 做幂等，解决 MQ 重复投递问题。对于失败消息，生产端通过 `next_retry_at` 做延迟重试，消费端多次失败后进入死信或补偿流程。
