# 售后工单与 SLA 履约平台：面试亮点总结

## 1. 项目介绍话术

这个项目是一个面向售后服务场景的工单履约平台，主要用于承接客服 Agent 无法自动解决的问题。用户问题会被转化为工单，系统根据问题分类、优先级和技能组进行派单，并通过 SLA 机制保证响应和解决时限。项目中我重点实现了工单状态机、SLA 超时升级、异步通知、可靠消息、全文检索和统计分析。

它和我的客服 Agent 项目形成前后衔接：Agent 负责前台问题理解和自动问答，工单平台负责后台人工履约和服务闭环。

## 2. 简历写法

简洁版：

> 设计并实现售后工单与 SLA 履约平台，支持工单创建、状态机流转、技能组派单、SLA 超时升级、异步通知、全文检索和统计报表。基于 Spring Boot、MySQL、Redis、RabbitMQ、Elasticsearch 构建核心链路，并通过 Outbox + 幂等消费保证消息可靠性。

强调 Agent 联动：

> 设计并实现客服 Agent 后置履约系统，将 Agent 无法解决的问题自动转化为售后工单，支持对话摘要、问题分类、优先级建议、技能组派单、SLA 超时升级和处理进度追踪，形成从智能问答到人工处理的完整闭环。

强调后端能力：

> 负责售后工单平台核心模块设计与实现，包括工单状态机、SLA 计时任务、Outbox 可靠消息、MQ 异步通知、Redis 缓存限流、Elasticsearch 搜索同步和 MySQL 索引优化。针对状态并发更新、消息重复消费、SLA 重复触发等问题设计了乐观锁、幂等表和条件更新方案。

## 3. 项目亮点

### 3.1 状态机驱动工单流转

普通 CRUD 系统可能直接修改状态字段，本项目使用动作驱动状态机。

可讲点：

- 工单状态不能任意跳转。
- 每个动作都有前置条件。
- 状态变更同时写操作日志。
- 使用乐观锁避免并发覆盖。

面试话术：

> 我把状态变更抽象成动作，例如分配、接单、转技术支持、标记解决、关闭等。接口层不能直接传目标状态，而是传动作，后端通过状态机判断当前状态是否允许执行该动作。这样可以避免已关闭工单继续处理、未分配工单直接解决等问题。

### 3.2 SLA 超时升级

可讲点：

- 创建工单时根据规则生成 SLA 任务。
- 定时任务扫描到期任务。
- 使用状态条件更新避免重复触发。
- 超时后通过 MQ 异步通知和升级。

面试话术：

> SLA 任务不是简单定时提醒，而是有自己的生命周期。任务初始是 `PENDING`，如果工单已响应或解决就取消；如果到期仍未完成，扫描任务会用 `WHERE status = 'PENDING'` 的条件更新把它标记为已触发，保证并发场景下只有一个线程能触发升级。

### 3.3 Outbox 可靠消息

可讲点：

- 业务数据和事件数据同事务写入 MySQL。
- 后台任务发布 MQ。
- 发布失败可以重试。
- 消费端幂等。

面试话术：

> 为了解决数据库提交成功但 MQ 发送失败的问题，我使用了 Outbox 模式。创建工单时，工单主表、操作日志和事件表在同一个事务里提交。之后由后台任务扫描事件表发送 MQ。这样即使 MQ 临时不可用，事件也不会丢，后续可以重试。

### 3.4 消费幂等

可讲点：

- MQ 至少一次投递会导致重复消费。
- 每条事件有唯一 `event_id`。
- 消费者用 `event_id + consumer_name` 做唯一约束。
- 插入失败说明已消费，直接返回成功。

面试话术：

> 我默认 MQ 可能重复投递，所以消费者不能依赖“只消费一次”。每个消费者处理事件前，先向消费记录表插入 `event_id + consumer_name`，如果唯一键冲突，说明这个消费者已经处理过该事件，直接返回成功。

### 3.5 MySQL 索引优化

可讲点：

- 客户按状态查自己的工单。
- 客服按负责人和状态查待处理工单。
- SLA 按状态和截止时间扫描。
- 避免深分页，可以使用游标分页。

面试话术：

> 我根据实际查询路径设计组合索引，而不是给每个字段单独建索引。比如客户查询工单列表使用 `(customer_id, status, created_at)`，客服工作台使用 `(assignee_id, status, priority)`，SLA 扫描使用 `(status, deadline_at)`。

### 3.6 Redis 使用克制

可讲点：

- Redis 不保存核心事实。
- 只用于缓存、限流、幂等 Token、短期计数。
- 缓存更新失败不影响主数据。

面试话术：

> 我没有把工单核心状态放在 Redis，核心数据仍然以 MySQL 为准。Redis 主要用于权限缓存、SLA 规则缓存、接口限流和派单时的短期负载计数，这样可以降低一致性复杂度。

### 3.7 Elasticsearch 搜索同步

可讲点：

- MySQL 负责精确查询和事务。
- Elasticsearch 负责关键词搜索。
- 通过 MQ 异步同步。
- 同步失败可重试。

面试话术：

> 工单列表的条件查询仍然走 MySQL，但标题、描述、处理记录、Agent 摘要等关键词搜索走 Elasticsearch。同步不是在接口里直接写 ES，而是通过工单事件异步消费，避免 ES 故障影响核心链路。

## 4. 高频面试问题

### 4.1 为什么不用微服务？

> 这个项目的核心复杂度在工单状态、SLA 和可靠消息上。第一版我选择模块化单体，是为了让事务边界更清晰，也降低部署复杂度。模块上已经按工单、SLA、通知、搜索、统计拆分，后续如果要演进成微服务，可以按这些边界拆。

### 4.2 如何保证工单创建后通知一定发送？

> 不保证通知同步发送成功，而是保证通知事件不丢。工单创建时会在同一事务中写入 Outbox 事件，后台任务负责发送 MQ。如果 MQ 失败，事件仍然在数据库里，可以继续重试。

### 4.3 如何防止重复通知？

> 消费端基于事件 ID 做幂等。通知表也可以增加唯一业务键，例如 `event_id + receiver_id + notification_type`，即使 MQ 重复投递，也不会生成重复通知。

### 4.4 SLA 任务重复扫描怎么办？

> SLA 任务可以被重复扫描，但不能重复触发。处理时使用条件更新：只有 `PENDING` 状态才能改成 `TRIGGERED`。如果多个线程同时处理，只有一个线程更新成功。

### 4.5 工单状态并发修改怎么办？

> 工单表有 `version` 字段，状态更新时带上版本号。如果更新影响行数为 0，说明状态已经被其他请求改变，需要重新读取后再判断。这样可以避免两个操作互相覆盖。

### 4.6 Agent 对接有什么价值？

> Agent 负责把用户自然语言对话转成结构化工单信息，包括摘要、分类、优先级建议和原始上下文。工单平台负责后续派单、SLA、处理和追踪。这样不是单纯问答，而是形成完整服务闭环。

## 6. 面试讲解顺序

推荐顺序：

1. 先讲业务背景：客服 Agent 解决不了的问题需要进入人工履约。
2. 再讲系统目标：工单创建、派单、SLA、通知、统计。
3. 接着讲核心设计：状态机、SLA、Outbox。
4. 然后讲技术细节：索引、Redis、MQ 幂等、ES 同步。
5. 最后讲遇到的问题和优化。
