# 智能客服 Agent 开发计划 v4.0

## 项目概述

项目名称：Smart CS Agent（智能客服 Agent）
技术栈：Java 17 + Spring Boot 3.3 + LangChain4j
项目目标：开发一个可写进简历、面试可深入讲解的 Agent 项目

---

## 核心原则

1. 聚焦：一次只做一个阶段，做完再规划下一步
2. 可验收：每个阶段有明确的验收标准
3. 可展示：每完成一个阶段都能运行和演示
4. 可讲解：每个功能都能在面试中说清楚

## Phase 3: 代码重构 + Skill 架构

### 目标

建立可扩展的 Skill 架构，为后续功能打好基础。

### 验收标准

1. Skill 策略包结构清晰，包含 manifest、策略说明、意图定义等
2. System Prompt 从代码移到文件，方便切换
3. AgentController 和 ChatApiController 整合，消除重复代码
4. 配置外部化，支持不同环境

### 需要完成的任务

#### 任务 3.1: 创建 Skill 策略包结构

创建文件结构：
```
skills/
└── customer-service/
    ├── manifest.yaml        # 元数据、能力声明
    ├── SKILL.md             # 主策略说明
    └── references/
        ├── persona.md       # 角色与表达风格
        ├── intent.md        # 意图分类定义
        ├── policy.md        # 对话策略
        └── templates.md     # 回复模板
```

#### 任务 3.2: 整合重复代码

- 合并 AgentController 和 ChatApiController 的重复 Agent 接口
- 统一 Agent 创建逻辑到 AgentFactory 或 AgentConfig
- 保留 LlmDemoController 用于对比学习

#### 任务 3.3: 配置外部化

- System Prompt 从代码移到文件
- 工具列表配置化
- 支持不同 Skill 切换

#### 任务 3.4: 添加配置类

创建 Spring 配置类：
- AgentConfig: Agent 创建配置
- SkillConfig: Skill 加载配置

### 面试话术

> 我采用了分层解耦的架构设计，参考了 MCP 的思想。
> Skill 层负责对话策略，Tools 层负责业务能力，两者通过接口解耦。
> 这样设计的好处是：新增业务场景只需加新的 Tool，Agent 核心不用改动。
> System Prompt 外置到文件，方便后续做 Skill 切换和 A/B 测试。

## Phase 4: 意图识别增强

### 目标

更准确地理解用户意图，为后续 RAG、记忆、多 Agent 打基础。

### 验收标准

1. 给定 10 个测试用例，意图识别准确率 ≥ 90%
2. 支持多种意图类型：查订单、查产品、申请退货、闲聊、其他
3. 返回置信度分数，方便后续路由决策

### 需要完成的任务

#### 任务 4.1: 定义意图分类

创建意图分类体系：
- ORDER_QUERY: 查询订单
- PRODUCT_QUERY: 查询产品
- RETURN_APPLY: 申请退换货
- USER_INFO: 查询用户信息
- CHITCHAT: 闲聊
- OTHER: 其他

#### 任务 4.2: 实现三路融合识别

三路识别 + 加权投票：
- LLM 识别：语义理解强，但成本高
- 关键词匹配：速度快、成本低，但不够灵活
- 规则匹配：确定性高，处理边界情况

加权投票：综合三路结果，取置信度最高的

#### 任务 4.3: 意图路由

根据识别结果路由到不同处理逻辑：
- 高置信度：直接执行
- 低置信度：询问用户确认
- 多意图：追问澄清

#### 任务 4.4: 测试用例集

创建意图识别测试用例：
```
输入: "帮我查一下订单 ORD-001"
预期: ORDER_QUERY (置信度 > 0.9)

输入: "有什么产品推荐"
预期: PRODUCT_QUERY (置信度 > 0.8)

输入: "我想退货"
预期: RETURN_APPLY (置信度 > 0.8)

输入: "你好"
预期: CHITCHAT (置信度 > 0.9)
```

### 面试话术

> 意图识别我采用了三路融合的方式：LLM 识别、关键词匹配、规则匹配。
> 三路各有优缺点，通过加权投票综合结果。
> 这样比单用 LLM 更准确、更稳定，也降低了成本。
> 对于低置信度的情况，会主动询问用户确认，避免误操作。

## Phase 5: RAG 知识检索

### 目标

Agent 能检索知识库回答产品和政策问题。

### 验收标准

1. 支持产品知识检索（价格、参数、描述）
2. 支持政策知识检索（退换货政策、配送说明）
3. 检索结果相关性高，能回答 80% 的知识类问题

### 需要完成的任务

#### 任务 5.1: 知识文档准备

创建知识文档：
```
knowledge/
├── products/
│   ├── bluetooth-headset.md
│   ├── smart-watch.md
│   └── ...
└── policies/
    ├── return-policy.md
    ├── shipping-policy.md
    └── ...
```

#### 任务 5.2: 文档加载与分块

- 加载 Markdown 文档
- 按段落或固定长度分块
- 保留元数据（来源、标题）

#### 任务 5.3: Embedding 向量化

- 选择 Embedding 模型（本地或 API）
- 将文档分块向量化
- 存储到向量数据库（可选 Chroma、Milvus 或内存）

#### 任务 5.4: 向量检索

- 用户问题向量化
- 计算相似度
- 返回 Top-K 结果

#### 任务 5.5: 检索结果注入 Prompt

- 将检索结果作为上下文注入
- LLM 基于上下文生成回答

### 面试话术

> RAG 采用了向量检索的方式：文档分块 -> Embedding -> 向量存储 -> 相似度匹配。
> 为了解决召回不全的问题，我计划后续加 Query Rewriting，
> 把用户问题改写成多个变体，提升召回率。
> 检索结果会注入到 Prompt 中，让 LLM 基于真实知识回答，减少幻觉。

## Phase 6: 三级记忆系统

### 目标

长对话不丢失上下文，支持跨会话记忆。

### 验收标准

1. 工作记忆：保留最近 5 轮完整对话
2. 短期记忆：提取关键信息（订单号、用户偏好）
3. 长期记忆：跨会话的用户画像
4. 记忆压缩：超过阈值自动摘要

### 需要完成的任务

#### 任务 6.1: 工作记忆（L1）

- 保留最近 5 轮完整对话
- 超出部分移入短期记忆

#### 任务 6.2: 短期记忆（L2）

- LLM 提取关键信息：订单号、产品名、用户偏好
- 摘要压缩：将旧对话压缩成摘要
- 存储在会话内

#### 任务 6.3: 长期记忆（L3）

- 用户画像：历史订单、偏好、常见问题
- 持久化存储（文件或数据库）
- 跨会话加载

#### 任务 6.4: 记忆检索

- 根据当前对话检索相关记忆
- 注入到 Prompt 中

### 面试话术

> 记忆系统采用三级架构：工作记忆、短期记忆、长期记忆。
> 工作记忆保留最近完整对话，短期记忆提取关键事实，
> 长期记忆存储用户画像。
> 这样平衡了上下文完整性和 token 成本。
> 超过阈值会自动压缩，用 LLM 生成摘要。

## Phase 7: 评测体系

### 目标

量化 Agent 质量，驱动持续优化。

### 验收标准

1. 有完整的测试用例集（至少 20 个用例）
2. 支持自动化评测
3. LLM-as-Judge 四维度打分
4. 生成评测报告

### 需要完成的任务

#### 任务 7.1: 测试用例集

创建评测用例：
```
{
  "input": "帮我查一下订单 ORD-001",
  "expected_tools": ["OrderTools.queryOrderStatus"],
  "expected_keywords": ["已发货", "蓝牙耳机"],
  "reference_answer": "您的订单 ORD-001 已发货..."
}
```

#### 任务 7.2: 过程指标评测

- 工具调用是否正确？
- 调用顺序是否合理？
- 是否有遗漏步骤？

#### 任务 7.3: 结果指标评测

LLM-as-Judge 四维度打分：
- 准确性（1-5 分）：回答是否正确？
- 完整性（1-5 分）：是否回答了所有问题？
- 相关性（1-5 分）：是否紧扣问题？
- 流畅性（1-5 分）：语言是否自然？

#### 任务 7.4: 评测报告

- 生成评测报告（JSON 或 HTML）
- 包含每个用例的得分和总体统计

### 面试话术

> 评测体系采用双层评测：过程指标和结果指标。
> 过程指标看工具调用是否正确，结果指标用 LLM-as-Judge 打分。
> 四个维度：准确性、完整性、相关性、流畅性。
> 这样能量化 Agent 质量，驱动持续优化。

## Phase 8: 多 Agent 编排

### 目标

支持复杂场景下的多 Agent 协作。

### 验收标准

1. 意图路由：根据意图分配到专门的 Agent
2. 降级策略：超时或失败时的兜底
3. 支持至少 3 个专门 Agent

### 需要完成的任务

#### 任务 8.1: 定义专门 Agent

- OrderAgent: 处理订单相关
- ProductAgent: 处理产品相关
- ReturnAgent: 处理退换货相关
- ChitchatAgent: 处理闲聊

#### 任务 8.2: 意图路由器

- 根据意图识别结果路由
- 支持置信度阈值
- 低置信度走默认 Agent

#### 任务 8.3: 降级策略

- 超时降级：返回兜底回复
- 失败重试：最多重试 2 次
- 熔断机制：连续失败时暂时关闭

#### 任务 8.4: 可观测性

- 调用链追踪
- 日志记录
- 性能监控

### 面试话术

> 多 Agent 采用意图路由的方式，根据用户意图分配到专门的 Agent。
> 每个 Agent 专注自己的领域，提示词和工具都是针对性配置的。
> 为了保证稳定性，实现了降级策略：超时返回兜底回复，连续失败时熔断。
> 加了可观测性，方便排查问题和优化性能。

做到可部署、可扩展、生产可用。

### 验收标准

1. 支持 Docker 部署
2. 配置外部化（环境变量、配置文件）

#### 任务 9.2: 配置外部化

- 环境变量管理敏感信息

#### 任务 9.3: 错误处理

- 全局异常处理

#### 任务 9.4: 性能优化

- LLM 响应缓存

- 输入过滤（敏感词、恶意输入）

#### 任务 9.6: Human-in-the-Loop

- 关键操作人工确认
- 会话转人工
- 人工审核队列

### 面试话术

> 生产化考虑了多个方面：Docker 部署、配置外部化、错误处理、性能优化。
> 安全方面有输入过滤和输出检查，防止敏感信息泄露。
> 关键操作支持 Human-in-the-Loop，需要人工确认。
> 这样才能真正上线使用。
