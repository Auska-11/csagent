模块一：Golang 基础数据结构
Q1：Go 的 slice 底层结构是什么？扩容机制是怎样的？（高）
● 核心关键词：三字段、指针/长度/容量、渐进式扩容、内存对齐
● 回答范式：
  a. 底层结构：slice 并不是基本数据类型，它是一个结构体，包含三个字段：
    ■ ptr：指向底层数组的指针。
    ■ len：当前已存储的元素个数（长度）。
    ■ cap：底层数组的总容量。
  b. 扩容机制（append 超出 cap 时触发）：
    ■ Go 1.18 之前：当 len < 1024 时，新容量变为原来的 2 倍；当 len >= 1024 时，新容量变为原来的 1.25 倍。
    ■ Go 1.18 及之后：采用更平滑的渐进式增长公式 newCap = oldCap + (oldCap + 3*256) / 4，避免了突变式的增长。
    ■ 扩容后会根据元素大小进行内存对齐（mallocgc），并将旧数据拷贝到新内存空间。
  c. 面试陷阱：
    ■ slice 是值传递，但拷贝的是结构体（ptr/len/cap），新旧 slice 共享底层数组，修改一个可能影响另一个。
    ■ 使用 copy() 可以实现真正的独立拷贝。

Q2：Go 的 map 底层原理是什么？为什么不是并发安全的？（高）
● 核心关键词：哈希表、hmap/bmap、拉链法、负载因子、并发不安全
● 回答范式：
  a. 底层结构：Go 的 map 底层是一个哈希表（Hash Table），核心结构体是 hmap：
    ■ 每个 bucket（bmap）最多存储 8 个 key-value 对，超出后挂溢出桶。
    ■ 使用拉链法解决哈希冲突。
    ■ 当负载因子（元素数/bucket数）> 6.5 时，触发渐进式扩容。
  b. 为什么不是并发安全的：
    ■ Go 的 map 没有内置任何并发保护机制（无锁、无原子操作）。
    ■ 多个 goroutine 同时读写同一个 map 时，会触发 fatal error: concurrent map writes。
    ■ 这是 Go 设计者的刻意选择——为了性能，默认不加锁。
  c. 解决方案：
    ■ map + sync.Mutex / sync.RWMutex：通用方案，适合读写均衡或读多写少。
    ■ sync.Map：专为读多写少、key 稳定的场景设计。
    ■ 分片 map：高并发场景，按 hash 分散到多个小 map，降低锁竞争。

Q3：sync.Map 的底层原理是什么？适用什么场景？（中）
● 核心关键词：读写分离、双 map、atomic、amended、dirty 提升
● 回答范式：
  a. 核心设计：sync.Map 采用了读写分离的设计，内部维护两个 map：
    ■ read map（readOnly）：只读部分，通过 atomic 原子操作访问，无锁。
    ■ dirty map：写入部分，需要通过 Mutex 加锁。
    ■ amended 标记：判断 read 中是否缺失某些 key，决定是否需要查询 dirty。
  b. 核心操作流程：
    ■ 读操作：先查 read map（无锁），未命中再查 dirty map（加锁）。
    ■ 写操作：如果 key 在 read 中已存在 → 原子更新（无锁）；如果 key 是新的 → 加锁写入 dirty。
    ■ 提升操作（dirty → read）：当 dirty 中的 key 数量 >= read 中的 key 数量时，触发提升，dirty 变为新的 read。
  c. 适用场景：
    ■ 适合：读多写少、key 相对稳定、很少新增/删除的场景。
    ■ 不适合：写多读少的场景（频繁加锁，性能反而不如 map + sync.RWMutex）。

Q4：Go 的 interface 底层原理是什么？（高）
● 核心关键词：eface/iface、_type/data/itab、类型断言、隐式实现
● 回答范式：
  a. 两种底层结构：
    ■ eface（空接口 interface{}）：只有两个字段 _type（类型信息）和 data（数据指针），可以存储任何类型的变量。
    ■ iface（带方法的接口）：包含 tab（*itab，存类型信息+方法表）和 data（数据指针）。
    ■ tab 里的 method 和 funcType 存的是函数指针，所以函数大小不影响接口大小。
  b. 赋值原理：
    ■ 变量赋值给空接口（eface）→ 调用 runtime.convT2E，申请内存并拷贝数据。
    ■ 变量赋值给带方法的接口（iface）→ 调用 runtime.convT2I，还会根据 type 和 method 组合生成 itab。
  c. 类型断言：
    ■ 语法 x.(T)：匹配成功返回 T 类型值，不匹配会 panic。
    ■ comma-ok 断言 v, ok := i.(T)：匹配失败 ok 为 false，不会 panic。
  d. 隐式实现：Go 的 interface 不需要显式声明 implements，只要目标类型实现了接口的所有方法，就自动实现了该接口。

模块二：Golang 核心机制
Q5：defer 的执行顺序和底层原理是什么？（高）
● 核心关键词：LIFO、链表、值拷贝、return 前执行、开放编码优化
● 回答范式：
  a. 执行顺序：defer 遵循 LIFO（后进先出）原则，后定义的 defer 先执行。
  b. 底层原理：
    ■ 每个 goroutine 维护一个 defer 链表。
    ■ 每次遇到 defer 语句，将函数包装成 _defer 结构体，插入链表头部。
    ■ 函数返回前，从链表头部依次取出并执行。
    ■ 核心函数：runtime.deferproc（注册 defer）、runtime.deferreturn（执行 defer）。
  c. 面试高频考点：
    ■ 执行时机：return 语句 → defer 执行 → 函数真正返回。
    ■ 参数在声明时求值：defer 的参数在注册时就已经确定（值拷贝），不是执行时才求值。
    ■ 闭包陷阱：defer 中如果使用闭包引用外部变量，引用的是变量的地址，可能在执行时拿到意外的值。
    ■ Go 1.14+ 优化：引入开放编码 defer（open-coded defer），对简单的 defer 直接在栈上分配，避免了链表开销。

Q6：Go 的 GC（垃圾回收）机制是怎样的？（高）
● 核心关键词：三色标记、混合写屏障、STW、并发标记清扫、GC Pacing
● 回答范式：
  a. 三色标记法：
    ■ 白色：未被扫描的对象，GC 结束后仍为白色的会被回收。
    ■ 灰色：已被扫描但其引用的对象还未全部处理完。
    ■ 黑色：已被扫描且所有引用都已处理完，确认存活。
    ■ 流程：从 GC Root 出发，标记所有可达对象为黑色，剩余白色对象被回收。
  b. 混合写屏障（Go 1.8+）：
    ■ 问题：并发标记阶段，goroutine 可能修改指针，导致存活对象被错误回收。
    ■ 方案：Go 使用混合写屏障，结合了 Dijkstra 插入写屏障和 Yuasa 删除写屏障，消除了栈重新扫描的需要。
  c. GC 阶段（四个阶段）：
    ■ Mark Setup（STW）：极短的暂停，开启写屏障并初始化。
    ■ Concurrent Marking：GC 与应用 goroutine 并发执行标记。
    ■ Mark Termination（STW）：极短的暂停，完成标记。
    ■ Concurrent Sweep：并发清扫白色对象，回收内存。
  d. GC Pacing（触发控制）：
    ■ 基于反馈控制机制，当堆增长达到 GOGC 设定的比例（默认 100%，即堆翻倍）时触发 GC。
    ■ Go 1.19+ 引入 GOMEMLIMIT，可设置软内存上限。
    ■ GC 动态调整 assist ratio，确保在内存耗尽前完成回收。

Q7：什么是内存逃逸分析？Go 在什么情况下会发生逃逸？（中）
● 核心关键词：编译期分析、栈分配vs堆分配、逃逸场景
● 回答范式：
  a. 概念：逃逸分析是编译器在编译期进行的一种分析，用来决定变量分配在栈上还是堆上。
    ■ 栈分配：函数结束后自动回收，零 GC 压力，速度快。
    ■ 堆分配：需要 GC 回收，速度较慢，但生命周期不受函数限制。
    ■ Go 默认优先栈分配，只有"逃逸"的变量才会分配到堆上。
  b. 常见逃逸场景：
    ■ 函数返回局部变量的指针：变量的生命周期超出了函数作用域。
    ■ 将变量赋值给接口类型：编译器无法确定大小，必须堆分配。
    ■ 闭包引用外部变量：闭包可能在函数返回后继续执行。
    ■ 发送到 channel 中的变量：不确定接收方何时使用。
    ■ 切片/map 中存储指针：可能被长期引用。
  c. 查看逃逸情况：go build -gcflags="-m" 可以查看编译器的逃逸分析结果。

Q8：Go 的 Context 原理是什么？（中）
● 核心关键词：树形传播、channel 通知、cancel/WithTimeout、资源释放
● 回答范式：
  a. 本质：context.Context 是 Go 标准库提供的机制，用于在 goroutine 之间传递截止时间、取消信号和请求范围的值。
  b. 四种创建方式：
    ■ context.Background() / context.TODO()：根 Context，通常在 main/init 中使用。
    ■ context.WithCancel(parent)：可手动取消，调用 cancel() 关闭 Done channel。
    ■ context.WithTimeout(parent, duration)：带超时，时间到期自动取消。
    ■ context.WithValue(parent, key, val)：携带键值对，适合传请求级元数据（如 traceID）。
  c. 取消传播机制：
    ■ Context 是树形结构，父 Context 取消时，所有子孙 Context 都会被取消。
    ■ 取消信号通过 Done() channel 广播，cancel() 会关闭该 channel。
    ■ 子 goroutine 通过 select 监听 ctx.Done() 来感知取消信号。
  d. 面试要点：
    ■ 必须调用 cancel()（通常 defer cancel()），否则关联资源不会释放，导致 goroutine 泄漏。
    ■ Context 是不可变的，WithXxx 返回新的 Context，不修改原 Context。
    ■ WithValue 不适合传业务参数，只适合传请求级元数据。

模块三：Golang 并发编程
Q9：GMP 调度模型是什么？（高）
● 核心关键词：G/M/P、本地队列、Work Stealing、Hand Off、抢占式调度
● 回答范式：
  a. 三个核心角色：
    ■ G（Goroutine）：协程，Go 中的轻量级线程，初始栈很小（约 2KB~8KB），可动态增长。
    ■ M（Machine）：操作系统线程，真正执行代码的实体。
    ■ P（Processor）：逻辑处理器，管理本地运行队列，数量默认等于 CPU 核数（GOMAXPROCS）。
  b. 调度流程：
    ■ P 维护一个本地队列（Local Run Queue），存放待执行的 G。
    ■ M 绑定一个 P，从 P 的队列中取 G 来执行。
    ■ 本地队列为空时，P 会从全局队列（Global Queue）或其他 P 的本地队列偷取 G（Work Stealing）。
  c. 关键机制：
    ■ Work Stealing（工作窃取）：空闲 P 从其他 P 偷取 goroutine，保证负载均衡。
    ■ Hand Off（交接）：当 M 因系统调用阻塞时，P 解绑并转移到空闲 M，保证其他 G 不被阻塞。
    ■ 抢占式调度：Go 1.14 引入基于信号的异步抢占机制，防止长时间运行的 G 独占 P（如死循环的 goroutine）。

Q10：Channel 的底层原理是什么？（高）
● 核心关键词：hchan、环形队列、互斥锁、等待队列、gopark/goready
● 回答范式：
  a. 底层结构（runtime.hchan）：
    ■ 环形队列（buf/sendx/recvx）：有缓冲 channel 使用环形队列存储数据，实现 FIFO。
    ■ 互斥锁（lock）：所有 channel 操作都需要先获取锁，保证并发安全。
    ■ 等待队列（sendq/recvq）：双向链表，存储被阻塞的 goroutine（sudog 结构）。
  b. 三种 channel 类型：
    ■ 无缓冲 channel（dataqsiz = 0）：发送和接收必须同步，发送方阻塞直到接收方准备好。
    ■ 有缓冲 channel（dataqsiz > 0）：缓冲区未满时发送不阻塞，未空时接收不阻塞。
    ■ nil channel（未初始化）：任何操作都会永久阻塞。
  c. 发送/接收流程：
    ■ 发送：加锁 → 有等待的接收者则直接拷贝并唤醒 → 缓冲区有空位则放入 → 否则挂起当前 goroutine（gopark）。
    ■ 接收：加锁 → 有等待的发送者则直接拷贝 → 缓冲区有数据则取出 → 否则挂起。
  d. 面试要点：
    ■ 向已关闭的 channel 发送数据会 panic。
    ■ 从已关闭的 channel 接收数据返回零值（不会 panic）。
    ■ channel 是引用类型，未初始化（nil）的 channel 操作会永久阻塞。
